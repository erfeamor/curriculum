## Why this exists

Split out of T-001 on 2026-08-13 (§2 of its original three-part scope), so a local-stack chore could not sit in the dependency path of the deployment chain. ~~`T-014` gates on T-001~~ — that clause is stale (corrected 2026-08-17): T-014's dependency on T-001 was removed later the same day, and T-001 is `done` regardless. The split still stands on its own merits; this task has never had a dependency of its own.

`docker-compose.dev.yml` still pins `mysql:8.0` while production runs **`mysql:8.4`** on the self-hosted container. Dev and prod disagreeing on the database major version is exactly the gap that lets a migration or a query pass locally and fail deployed.

## Scope

- Bump `docker-compose.dev.yml` to `mysql:8.4`.
- **The existing `cv-dev-mysql-data` volume was created under 8.0.** Either `docker compose down -v` (dev seed data is regenerated by the Flyway callback, so this costs nothing) or rely on MySQL's in-place 8.0→8.4 upgrade. Whichever is chosen, write it into the repo docs — the next person to hit a dirty volume should not have to rediscover it.
- Re-run the local stack and the E2E smoke.
- **Boundary — this task owns the meta repo's pin only.** Added 2026-08-22: the review that filed [T-152](T-152-mysql-84-parity-cv-database.md) found **three** `mysql:8.0` pins, not one. The other two live in `cv-database` (`docker-compose.yml:3` and, more consequentially, `Jenkinsfile:18` — the throwaway MySQL every migration is validated against) and are **T-152's**, filed separately because a `Jenkinsfile` diff forces `security_review: true` under adapter §5 while this one does not. Parallel-safe: different repos, no shared file.
- **`scripts/qa-env-override.py:555` takes this file as its base**, so this pin is also what every dev-loop stage-4 QA stack has been running. Four checkpoints on this board record QA against *"live MySQL 8.4"* ([T-102](T-102-education-resource.md):17/:137, [T-103](T-103-skills-catalog-and-assignments.md):97/:260) — the generator has no image handling, so those were most likely 8.0 wearing an 8.4 label, and the stacks are gone so it is not reconstructible. ### 4 · Coverage risks — what passes this plan and is still broken

- **AC "runs `mysql:8.4`" is satisfiable by the compose file alone.** A grep passes even if the image never pulled, or a stale local cache serves 8.0 layers, or the developer tested against a manually-run 8.0 container never torn down. This is precisely the T-102/T-103 failure. **QA-T016-01 is a diff sanity check and nothing more**; only 05/06/11 are proof.
- **The generator-inheritance criterion names only the version.** A QA stack can report 8.4 with Flyway silently failed or seeds not fired and still satisfy it. QA-T016-12 closes this — flagged because the criterion is **under-specified relative to its own intent**.
- **"Documented wherever the dev-stack commands live" names no file** — close to unfalsifiable. QA will check README.md, meta CLAUDE.md, or a compose header comment. **Developer should pick a canonical location up front** rather than leave QA to guess.
- **QA-T016-08 depends on the exact seed fixture for person 1.** If `cv-database/sql/dev-seeds/` changes concurrently this false-fails; check the seed file before blaming the bump.
- **A green Flyway exit does not distinguish "applied everything" from "applied 0 because it thought all were applied."** Read the migration count from the log everywhere, never the exit code.
- **Re-running the slot stack reuses its named volume**, masking "from an empty volume" on run 2+. `down -v` before every fresh bring-up.

### 5 · Failure signatures — several fail silently

| Failure | Signature | How to tell it apart |
|---|---|---|
| JDBC URL missing `?allowPublicKeyRetrieval=true` | **Does not error — hangs.** Repeated retry/"Waiting for database" lines, no distinct message, long stall then non-zero exit | Grep for "Public Key Retrieval is not allowed"; the tell is the multi-minute stall, versus the fast, loud failure below |
| MySQL 8.4 auth-plugin default change | Fails **fast** at connect: `Access denied`, or a plugin-load error, or a caching_sha2 RSA error distinct from the above | Not expected — the stack uses the `caching_sha2_password` default in both versions. Confirm by inspecting: `SELECT user, plugin FROM mysql.user WHERE user='cv';` → expect `caching_sha2_password`. Read the actual message; do not infer from log absence |
| Unrelated connect failure (bad password, port clash) | Also fast, but names credentials/host/port rather than a plugin or RSA term | Cross-check compose env and `docker compose -p cvdl_T-016 ps` for the expected slot ports before blaming 8.4 |
| Stale Docker cache serving 8.0 under the new tag | `mysql --version` says 8.0 while the compose file says 8.4 | Exactly why 05/06/11 read the running container. `docker pull mysql:8.4` and retest — an environment artifact, but it must still be caught before sign-off |
| In-place upgrade crash-loop | `mysql` restarts repeatedly, or logs data-dictionary / InnoDB redo-log incompatibility | Covered by QA-T016-14; if hit, that is the strongest argument for documenting the wipe path |

### The bump is provably safe, not merely observed to work

The data-layer reviewer applied `V1__init_schema.sql` plus the `afterMigrate` seed callback through Flyway 10 against real `mysql:8.0.46` **and** `mysql:8.4.11`, then diffed the whole `information_schema` picture: columns (type, charset, collation, nullability, default, extra), tables (engine, collation, row format), every index including `person_skill`'s composite PK, `@@sql_mode`, `@@character_set_server`, `mysql.user.plugin`, the Flyway history and all six row counts.

**Byte-identical except the `SELECT VERSION()` line.** Since the metadata Hibernate reads is unchanged, `ddl-auto: validate` cannot behave differently — that is a proof, where "the service booted" would have been an observation.

It also closed a gap production's success does **not** cover: `docker-compose.dev.yml:53` uses `jdbc:mysql://mysql:3306/cv` with **no** `allowPublicKeyRetrieval`, unlike production's URL. Connector/J 8.3.0 was run against both servers with that exact URL — `ssl_cipher=TLS_AES_256_GCM_SHA384` on both. Auto-generated TLS covers `caching_sha2_password` on 8.4, so the paramless dev URL is fine and the [T-023](T-023-meta-docs-stale-bff-smoke-path.md)-adjacent worry does not apply here.

### Two review findings, and one of them voided an H1 ruling

Found independently by both reviewers:

1. **`down -v` blast radius understated.** It drops *every* named volume in the project — `cv-dev-grafana-data` included — and `cv-observability/grafana/provisioning/dashboards/` ships only `dashboards.yml`, **no dashboard JSON**. A UI-built dashboard has no repo backup. The doc said it discarded "the old datadir".
2. **"Nothing is lost" was false, and the wipe ruling had lost its premise.** H1 ratified *"wipe is the supported route, seeds regenerate so it costs nothing"* — on QA's stage-0 recommendation, made while everyone still believed **8.4 would refuse an 8.0 datadir**. Once the asymmetry proved inverted, in-place became the safe forward path and nobody re-derived the ruling. Meanwhile `cv-admin-react` writes real rows to this same database, so a wipe destroys authored data.

   Corrected in `b3aea99`: **forward (8.0→8.4) in-place preserves the datadir, wipe optional; backward (8.4→8.0) wipe required.** The empirical log-line bullets were left verbatim — they were the most valuable part.

**This is the board's signature failure in its purest form yet**: not a stale number or a stale status, but a *ratified decision whose premise died three hours later*. It was made at a human gate, by the driver presenting it, on advice that was correct when given.

**A methodological catch worth keeping:** `information_schema.tables.table_rows` is an *estimate* for InnoDB and read 0 for a table holding a row. QA used `COUNT(*)` throughout instead — otherwise this pass would have reported false data loss on the one check whose entire purpose is proving data survives.
